# decisions

## Concepts
* [Bake core data into /var/lib/mysql instead of loading at first start](bake-data-vs-initdb.md) - The final image contains an already-initialized data directory; no /docker-entrypoint-initdb.d scripts are used at all; users are created in the builder stage and runtime password overrides go through a generated --init-file.
* [A browsing console — a landing page linking four preconfigured database UIs, run by Compose](browsing-console-stack.md) - Ship phpMyAdmin, Adminer, DbGate and CloudBeaver alongside the image as an opt-in Compose profile, fronted by a static landing page generated from the megasamples registry, bound to loopback and connected as the read-only demo user.
* [Build orchestration with make, Compose profiles and BuildKit](build-orchestration.md) - A Python package (`python3 -m megasamples <command>`) drives every step, `make` targets are one-line shims over it, one configuration file names what to build, and verification runs on the build machine in Docker with no CI service.
* [Chinook conversion path - run the upstream MySQL script with a NVARCHAR-to-utf8mb4 rewrite](chinook-conversion-path.md) - Use Chinook_MySql.sql v1.4.5 as-is except for replacing NVARCHAR with VARCHAR CHARACTER SET utf8mb4, an explicit utf8mb4 CREATE DATABASE, and (optionally) the lowercase database name.
* [Contoso conversion path - published csv-100k archive in core, csv-1m/10m in extended, MySQL DDL derived from SQLBI's SQL Server scripts](contoso-conversion-path.md) - Download SQLBI's ready-to-use CSV 7z (no generator run), map the Data-schema DDL to MySQL, load with LOAD DATA; the old Microsoft ContosoRetailDW .bak is not used.
* [Database naming convention and account model](database-naming-convention.md) - One MySQL database per dataset named in lower snake_case after the dataset, with a shared read-only demo user and a read-write admin user.
* [Dell DVD Store 3 conversion path - upstream MySQL DDL plus server-side LOAD DATA of the committed Small CSVs; reviews split to extended](dvdstore-conversion-path.md) - Reuse mysqlds3_create_db/ind/sp with InnoDB and utf8mb4 fixes, load the ~6.5 MB DS2-part CSVs into the build server during `make dvdstore`, defer the 190 MB reviews CSVs to the extended tier, drop the broken RESTOCK trigger.
* [Employees conversion path - concatenate schema and dumps into plain SQL, verify with SHA-256](employees-conversion-path.md) - Replace the mysql-client `source` directives with a single generated SQL stream; drop `flush binary logs`; run test_employees_sha2.sql as the acceptance test.
* [MySQL is the hub; PostgreSQL and SQLite are ports of the verified MySQL corpus](engine-hub.md) - Every converter emits MySQL SQL and the MySQL build server is where a dataset is loaded and verified; other engines are built from that corpus (schema from information_schema, data from the MySQL Shell dump) and verified against the same pinned expectations.
* [Enron — parse the CMU maildir with Python's email stdlib into a three-table schema](enron-conversion-path.md) - Choose a purpose-written parser over reusing third-party SQL dumps for the Enron corpus.
* [Indexing strategy and order of operations](indexing-strategy.md) - Carry upstream keys and indexes faithfully; derive indexes for index-less sources from key candidates, join columns, and range columns; load first, index second, constrain last; verify with information_schema and EXPLAIN.
* [Jaffle Shop conversion path - ship the classic Apache-2.0 seeds as generated INSERTs; jafgen run for larger data in extended](jaffle-shop-conversion-path.md) - Core = three classic CSVs (312 rows) converted to SQL at build time with explicit DDL; extended = jafgen-generated multi-year data loaded from CSV; do not vendor the unlicensed new-repo seeds.
* [Lahman conversion path - vendor SABR's 2025 CSV release, load with explicit DDL](lahman-conversion-path.md) - Use the SABR Version 2025 CSV set (not the SQL Server .bak, not the Access .mdb, not GitHub mirrors), commit the files under CC BY-SA 3.0, strip BOMs, load with LOAD DATA / generated INSERTs into typed tables with composite keys.
* [Conversion path for the large public tabular datasets](large-tabular-conversion-path.md) - DuckDB reads Parquet/CSV and emits typed MySQL-ready CSV; server-side LOAD DATA (strict) writes it, util.importTable only above 5 M rows. One pipeline for TLC, BTS, Chicago, Citi Bike and Divvy.
* [A live feed is taken as served: its dataset's tests describe a snapshot, and hold a build to floors and structure](live-artifacts.md) - The maintainer's decision of 2026-09-17 for artifacts whose upstream changes (chicago_crimes, a query against the city's portal) -- a build downloads what the feed serves that day, records what it got and never re-pins; the dataset's tests are floors and structure rather than a snapshot's bytes; nothing is mirrored, so the repository stays small and bakes in no stale data.
* [Conversion path for AdventureWorks OLTP, DW and LT - load the upstream CSV files directly, no SQL Server](mssql-adventureworks-conversion-path.md) - The repository's install-script form ships UTF-8 CSVs (OLTP 69 files / DW 30 files, 2025 edition) and the 2012 release ships an LT script zip; DDL is translated from the scripts and data loaded with LOAD DATA, avoiding .bak restores entirely.
* [Conversion path for Northwind and pubs - translate the T-SQL install scripts directly](mssql-northwind-pubs-conversion-path.md) - Both datasets are single self-contained T-SQL scripts with inline data, so the build translates them to MySQL DDL/DML with a script (no SQL Server, no bcp).
* [Conversion path for WideWorldImporters and WideWorldImportersDW - one-off restore in a SQL Server container, export, cache the artifact](mssql-wideworldimporters-conversion-path.md) - WWI data exists only inside .bak/.bacpac files (transactional rows are generated by randomised T-SQL), so the build restores the Standard .bak files in the Developer-edition container on an amd64 builder, exports UTF-8 delimited files with bcp/sqlcmd, loads MySQL, and pins the exported artifact so later builds skip SQL Server.
* [No release assets: the repository is what is published, and every byte of data comes from its upstream to the user's machine](no-release-assets.md) - The maintainer publishes only the repository -- no data-v1 mirror of upstream artifacts, no SQLite file set -- so nothing the project builds is redistributed by it; what a script cannot fetch (the lahman zip behind a share link) the user obtains by hand, and an upstream that has moved since it was pinned (the Chicago 2024 extract) is accepted explicitly with MEGASAMPLES_ACCEPT_DRIFT=1, which re-pins the manifest, after which the dataset's expectations are re-pinned from the MySQL build.
* [Oracle sample schemas — convert from the plain scripts/CSVs with a Python converter; Oracle Database Free only as an optional verification profile](oracle-conversion-path.md) - For HR, CO, SH and OE the upstream artifacts are plain INSERT scripts and RFC-4180 CSV files, so no Oracle product is needed; an opt-in build-oracle Compose profile (Oracle Database Free + python-oracledb) is reserved for cross-checking row counts and checksums.
* [How the PostgreSQL image is shaped: one database per dataset, a baked cluster, the same two accounts](postgres-image-shape.md) - The PostgreSQL engine ships a cluster initialised and loaded in a builder stage at the official image's own PGDATA, with demo and admin roles, a megasamples registry database and a wrapper that applies password overrides at start.
* [Views, routines, triggers, full-text and spatial indexes are ported to every engine, and each exception is recorded with its reason](programmable-object-parity.md) - The PostgreSQL and SQLite ports carry the MySQL corpus's views, stored routines (PostgreSQL), triggers, ON UPDATE columns, FULLTEXT indexes and REGEXP checks through deterministic translators, verified by executing them against outputs pinned from MySQL; what an engine cannot carry is dropped by name with the reason, and the seven kinds of exception are listed here.
* [Repository layout, committed versus downloaded content, and the download manifest](repository-layout.md) - One Python package for the pipeline, one directory per engine and per console, one directory per dataset with its contract, converter, tests, licence and provenance; upstream artifacts and every build output live in git-ignored folders, fetched through a single YAML manifest.
* [Dispositions of the first code review (Claude code-review and GitHub Copilot) on PR #1](review-2026-09-02-dispositions.md) - Every finding from the first two reviews (and the second Copilot pass) validated against the original request, classified, and resolved as a class or explicitly declined with the reason; the conventions runbook revision 2 came out of this pass.
* [Dispositions of the release-2 code review (Claude code-review, 2026-09-10)](review-2026-09-10-dispositions.md) - The fifteen confirmed defects the review of the release-2 branch reported (six that break a fresh build or a documented command, five wrong behaviours in what ships, four in reproducibility and checks), each verified against the code and fixed; the four latent translator defects it listed beyond its cap; and the one it named that was not verified.
* [Sakila conversion path - load the upstream scripts unmodified](sakila-conversion-path.md) - Sakila is MySQL-native; run sakila-schema.sql then sakila-data.sql through the mysql client with no transformation; pin inner-file checksums.
* [Mapping SQL Server multi-schema databases (AdventureWorks, WideWorldImporters) into MySQL](schema-to-database-mapping.md) - MySQL has no schema level below the database; AdventureWorks (5 schemas) and WideWorldImporters (4 data schemas) map to one database per dataset with lower-cased schema-prefixed table names (option A, accepted).
* [Small teaching datasets (titanic, iris, penguins) - one database each versus a shared `smallsets` database](smallsets-database-layout.md) - Titanic, Iris and Palmer Penguins live as tables in one database named smallsets (option 2, accepted), following the naming convention; separate databases were considered and rejected.
* [How the SQLite port is shaped: one file per database, written by the stdlib driver, shipped in a data image](sqlite-file-conventions.md) - Each database becomes <name>.sqlite with MySQL-like declared types, inline constraints, secondary indexes, a rollback journal and an application id; the files ship in an Alpine image carrying the sqlite3 shell and stay under build/sqlite/ for use without a server.
* [SSB data is generated by eyalroz/ssb-dbgen built with EOL_HANDLING=ON in a builder stage; queries re-typed from the paper](ssb-generator-path.md) - Choose the generator for the ssb database among the ssb-dbgen forks and a SQL derivation from TPC-H data.
* [One configuration file names the stack; the chooser writes it and compose.yaml is generated from it](stack-configuration.md) - megasamples.yaml holds the engines, the datasets per engine and the consoles; an interactive configurator writes it, every command reads it, and compose.yaml is generated so the running stack is exactly what was chosen.
* [Stack Exchange — build from the archive.org 2024-04-02 snapshot with an own streaming XML loader](stackexchange-conversion-path.md) - Choose the last click-through-free public dump and a purpose-written MySQL loader over the profile-page dumps and the Postgres converter.
* [Target MySQL version is 9.7 LTS, pinned to the latest published official image point release](target-mysql-version.md) - Choose MySQL 9.7.x LTS (currently 9.7.3 upstream, 9.7.2 in the official image) over 8.4.x LTS as the image base.
* [Target PostgreSQL version is 18, pinned to the official image's 18.6 bookworm variant](target-postgres-version.md) - The PostgreSQL engine is built from postgres:18.6-bookworm, the newest stable major the official image publishes; 19 is a beta.
* [Row-count, sample, and aggregate-checksum test method](test-checksum-method.md) - A single canonical row-digest definition computed identically in Python on the source side and in SQL on the MySQL side, aggregated order-independently with BIT_XOR and SUM, plus per-column aggregates and deterministic samples.
* [Final tier assignment per dataset](tier-assignments.md) - Which datasets are baked into the core image, which are extended (downloaded, generated, or user-fetched), with the size evidence behind each call.
* [Two distribution tiers, core and extended, and the opt-in mechanism](tier-model.md) - Core datasets are baked into the image; extended datasets are fetched or generated on demand through Compose profiles and make targets.
* [TPC-C population uses sysbench-tpcc (Apache-2.0 scripts on the packaged GPL sysbench), with HammerDB TPROC-C as reference and fallback; tpcc-mysql rejected](tpcc-implementation-choice.md) - Pick the open-source loader that creates and fills the tpcc database in the loader container.
* [TPC-DS data is generated by DuckDB's dsdgen port (fractional SF), queries by tpcds-kit dsqgen with a three-line mysql dialect file](tpcds-generator-path.md) - Choose the generator and query source for the tpcds database among tpcds-kit (C, integer SF only) and DuckDB's tpcds extension.
* [TPC-H data is generated by DuckDB's dbgen port, cross-checked against tpch-kit, and loaded from pipe-delimited files](tpch-generator-path.md) - Choose the generator and load path for the tpch database among tpch-kit (C), electrum/tpch-dbgen, and DuckDB's tpch extension.
* [Ship Simple English Wikipedia rather than a Wikidata extract](wikidata-vs-wikipedia-simple.md) - Between the two Wikimedia text-heavy candidates, recommend Simple English Wikipedia (356 MB artifact, MySQL-native link tables, CC BY-SA) over any Wikidata extract (43-253 GB official dumps, no reproducible small subset).
* [Simple English Wikipedia — load the MediaWiki .sql.gz tables directly and synthesize revision/text from pages-articles XML, keeping the binary schema](wikipedia-simple-conversion-path.md) - Choose direct SQL loading with DDL fix-ups plus a streaming XML parse, and keep MediaWiki's varbinary/binary columns with utf8mb4 views rather than converting in place.
