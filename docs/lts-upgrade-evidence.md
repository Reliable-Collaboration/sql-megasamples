# DL-074: correct the upgrade to supported LTS targets

This supersedes the release-selection decisions in the four historical engine, client, dataset and cold-readiness reports; their receipts remain intact. The branch starts at `ab75c45a82cee444d2652581d6db151e1d5a3b98`, after fetching `origin`. The live deployment has not been changed. Work is still in progress; final validation and merge are pending.

The owner requires the newest LTS line reachable by a supported upgrade path, at its latest patch. If no eligible LTS exists, use the latest supported release of the current major. Vendor release numbers are not interchangeable: the selected MySQL server/C API is 9.7.4, Shell is 9.7.1 and Connector/J is 9.7.0. Oracle's policy gives connectors and Shell one upstream release track rather than independent LTS lifecycles. Selecting their available 9.7 releases follows the owner's explicit instruction; it does not invent an Oracle promise of continued 9.7 connector security fixes.

Oracle’s [release notes](https://dev.mysql.com/doc/relnotes/mysql/9.7/en/news-9-7-4.html), read 2026-11-17T16:46:19Z, identify 9.7.4 as released and 9.7.4.1 as not yet released. The MySQL server is pinned from Oracle Container Registry: `container-registry.oracle.com/mysql/community-server:9.7.4@sha256:cb9cfddeccbbd9922bf927cd67bdb58067b357a1fc75d132988d1f5cc4cb17bb` (registry read 2026-11-17T15:40:01.485365+00:00). Oracle’s image bundles Shell 26.10.0, so `engines/mysql/base.Dockerfile` replaces the entire Shell payload with 9.7.1 from digest-pinned `docker.io/library/mysql:9.7.4@sha256:df90258da46f6e7ff8574ff84f17618aba0765cac749928299c69fd4e7cb8ad8`. The payload includes its libraries, Python runtime, authentication plugins, helper paths, manual and licence documentation. A file-level audit caught missing auxiliary files in the first thin-base attempt. The completed base also extracts Oracle’s SHA-256-checked 9.7.4 full-client RPM for mysqlbinlog/mysql_config_editor and points Shell’s helper paths to those current-patch binaries; stock 26.10 helper versions and corrected 9.7.4 versions were both probed. The thin base preserves the existing data-volume convention, adds the project configuration include and adapts the entrypoint path. A real configuration probe failed before the include fix and passed afterward. The server and baked images both build/use that same thin base; the loader copies only the Oracle-registry native CLI binaries. Both registry manifest digests were verified against their response bytes. The first 9.7.4 build server was initialized from scratch using Docker Hub’s Oracle distribution. The final Oracle-registry thin base initialized a fresh build-server directory and restored all 30 physical databases from those new 9.7 logical dumps in 963.70 seconds before baking. Its first attempt to restore an old 26.10 dump Failed with Shell error 53011 (version mismatch). No `ignoreVersion` bypass was used: all 33 configured MySQL datasets passed rebuilding from the unchanged downloaded inputs and previously authorized WWI exports. No 26.10 data directory is reused.

Node 26.13.1 is the newest upstream LTS but failed to compile DbGate's bundled ssh2 native binding (`v8::Context::GetIsolate` was removed). Node 24.22.3 is the newest tested compatible LTS; the image rebuilds native bindings and opens SQLite under the new ABI. Both the failed candidate and successful native-binding probe are retained. npm's new install-script approval mechanism initially skipped native rebuilds; explicit version-pinned approvals and direct native-module loading now verify that the build actually ran. These are build-script approvals, not acceptance of vendor service/database terms.

DuckDB 2.0 is already an LTS release, so it stays at 2.0.0. SQLGlot's publisher metadata now lists 30.33.0 in major 30; its exact requirement and `uv.lock` were updated with `uv lock --upgrade-package sqlglot`, inside the tools container. NGINX has no LTS designation in the consulted branch policy; current-major latest Mainline 1.31.8 replaces 1.30.6. phpMyAdmin's old 4.9 LTS is not a supported upgrade from deployed 5.2 and requires PHP below 8.0, so its supported 5.2.3 application/runtime stays.
