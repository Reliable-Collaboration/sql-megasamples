# The read-only `demo` account

PostgreSQL's `demo` is read-only by PostgreSQL's own model. It holds the built-in role `pg_read_all_data`, which reads every table, view and sequence in every database it can connect to, and no write privilege: none granted directly, none through a role it belongs to (`megasamples_working_read`, which gives it `CONNECT` on the sample databases, writes nothing), and no default privilege that would give it one. Every `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `CREATE` in a sample schema and `DROP` is refused with SQLSTATE `42501`. Otherwise PostgreSQL's defaults stand: `demo` may create temporary tables, call built-in functions and create large objects of its own, none of which changes a sample. A copy is closed to `PUBLIC` by the copy command as it is made, so `demo` cannot connect to it.

`tests/test_postgres_demo_native.py` checks natively that `demo` holds `pg_read_all_data` and no role that writes (`pg_write_all_data`, `admin` or `postgres`), that no default privilege gives it a write, that it reads every sample table, that `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE`, `CREATE TABLE` in a sample schema and `DROP` are each refused with `42501`, and that it keeps PostgreSQL's defaults (temporary tables, built-in functions, its own large objects). It also runs, as `demo`, every catalog, describe, snapshot and data-read statement of DataIntent's PostgreSQL adapter on chinook, northwind and pubs: a change to `demo` that breaks that consumer fails there first. Run it with `POSTGRES_DEMO_NATIVE=HOST:PORT` naming a server from this image. The copy cases are in the TCP copy suite (`tests/test_v1_server_copy.py`): `demo` is refused `CONNECT` on a fresh copy with `42501`, and a copy whose closure fails is reported `create-unsettled` and accepts no connection.

MySQL gives `demo` exactly `SELECT, SHOW VIEW` on the working schemas and on explicitly enabled foreign namespaces (each pattern's underscores escaped), `SELECT` on the registry tables `megasamples.datasets` and `megasamples.copy_service`, and `USAGE`; nothing on other schemas, and no `CREATE TEMPORARY TABLES`, stored-routine `EXECUTE`, write, grant or administrative privileges. The image's own grant generator (`megasamples/mysql_templates.py`) is the source, and `megasamples test-image` and the native suite assert the exact set. *(The evidence of 2026-11-18 below was taken when `demo` held `SELECT, SHOW VIEW ON *.*`.)* The tests inspect its actual grants and attempt temporary-table creation and every direct stored-routine call. Writer grants remain unchanged. These are server account grants, not a SQL statement classifier: ordinary session control and MySQL built-ins are not governed by stored-routine `EXECUTE` ACLs. The executable [boundary probe](validation/strict-read-mysql-boundary.py) was written for the earlier grant: it confirmed persistent write/DDL denials in every sample database and that `demo` can acquire and release a built-in named lock. It is kept as it was: it asserts the earlier `SELECT, SHOW VIEW ON *.*` grant, so it fails at its grant assertion on this release, before any denial or lock check. This release's grants are checked by `megasamples test-image` and the native suite. The strict named-lock denial criterion is **Failed**. Enforcing “only reads” across these MySQL built-ins is **Unsupported by stored-routine grants**. It would require an additional statement/function restriction layer, which this project does not supply. MySQL documents [named locks](https://dev.mysql.com/doc/refman/9.7/en/locking-functions.html) separately from [stored-routine execution privileges](https://dev.mysql.com/doc/refman/9.7/en/privileges-provided.html), read **2026-11-18 09:56:36 UTC**. SQLite has no server accounts; a read-only client must open its files read-only. Its [omitted SQL features](https://www.sqlite.org/omitted.html), read **2026-11-18 10:56:21 UTC**, document the absence of GRANT/REVOKE.

Run native privilege tests with `MEGASAMPLES_NATIVE_READ_TESTS=1` after sourcing the supplied environment. `tests/test_strict_read_native.py` requires `DL077_ISOLATED_GRAPH` (the isolated store, checked first), each engine's container named in `STRICT_READ_POSTGRES_CONTAINER` or `STRICT_READ_MYSQL_CONTAINER`, and `STRICT_READ_OWNER`, which each container's ownership label must equal; it then uses only the container IDs it checked. The checkout's `megasamples.yaml` must name the image's own dataset selection. The suite checks it per database against the image's registry, which has one row per database, so an `append: true` dataset counts with its base and its own tables are not checked this way, and dataset-specific cases run only where the selection holds their dataset. Regular `make test-image` checks also cover demo's `pg_read_all_data` membership. The canonical dataset matrix runs counts, fingerprints, foreign-key/index checks and views as `demo`. At each reset checkpoint a supplementary native matrix reads every complete table: PostgreSQL folds native row MD5 values, MySQL uses native extended table checksums, and SQLite checks both runtime files by SHA-256. These reset fingerprints compare within an engine; they do not replace the repository's canonical cross-engine fingerprints.

The privilege model follows the [PostgreSQL privilege documentation](https://www.postgresql.org/docs/18/ddl-priv.html), the [database creation documentation](https://www.postgresql.org/docs/18/sql-createdatabase.html) and the [MySQL privilege documentation](https://dev.mysql.com/doc/refman/9.7/en/privileges-provided.html). This change makes no new engine-version or vendor-support claim.

MySQL also has a view-delegation gap: the native [view-session-state probe](validation/strict-read-mysql-view-state.py) records **Failed** because evaluating the employee views sets `@max_date` in the demo session. The views use definer context, so refusal of direct routine calls does not establish refusal of those indirect helper calls. The [MySQL security-context documentation](https://dev.mysql.com/doc/refman/9.7/en/stored-objects-security.html), read **2026-11-18 11:29:48 UTC**, explains this distinction. This release changed `demo`'s MySQL grants (above) but not these views, and the gap still holds under them; neither this behavior nor stateful built-ins are certified as strict reads.

An earlier build enforced a stricter profile with a server extension and a routine allowlist; its [evidence page of 2026-11-18](history/strict-read-evidence.md) and the receipts under `validation/` describe that build. That profile also relied on PostgreSQL's [routine defaults](https://www.postgresql.org/docs/18/sql-alterdefaultprivileges.html) and [volatility documentation](https://www.postgresql.org/docs/18/xfunc-volatility.html), read with the hook API and source at **2026-11-18 06:32:51 UTC** ([source receipt](validation/strict-read-sources.json)).
