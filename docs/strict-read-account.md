The `demo` account reads the sample data. PostgreSQL initialization removes database `TEMPORARY` and routine `EXECUTE` inherited from `PUBLIC`, then grants the reviewed routine floor to `PUBLIC`. `admin` receives explicit temporary-object rights for write workloads; its previous effective routine rights are preserved before removing the public grants. The superuser retains its rights. This policy applies to the registry, maintenance database, sample databases and both templates.

The built-in read policy lives in [read-routine-names.sql](../engines/postgres/init/read-routine-names.sql). Each name has a reason. Initdb operators and casts also retain their nonvolatile implementation functions; selected upstream `information_schema` helpers retain execution for column and key metadata. The family list admits immutable and stable overloads in `pg_catalog` with initdb object identifiers and without `SECURITY DEFINER`. Exact-signature grants add `pg_database_size(oid)` and `pg_export_snapshot()`. One routine is granted to `demo` directly rather than to `PUBLIC`: `megasamples_policy_loaded()` in `pg_catalog`, the healthcheck's report that the policy library was preloaded (design 4.2, P-8); `admin` and every other role except the superuser `postgres` are refused it. An exported snapshot remains importable until its exporting transaction ends. Metadata helper definitions were checked against the upstream source. No user routine qualifies merely because it declares itself `STABLE`. Large-object creation and import, sequence advancement, configuration changes, advisory-lock routines and server management stay outside the public routine floor. The SQL `NOTIFY` statement remains available. The [version 1 inventory](validation/dl-077-v1-public-routines.md) gives each signature `demo` can execute and its reason; PR #14's 2026-11-18 inventory stays as [that PR's evidence](validation/strict-read-executable-routines.md). PR #14's [evidence page](strict-read-evidence.md) and its receipts describe this guide and the policy files as they were at `2879fc472ad1`.

The policy deliberately excludes transaction-ID allocation (`txid_current` and `pg_current_xact_id`), although these built-ins are classified `STABLE`. It retains query arithmetic, text/date/JSON transformations, aggregates, window functions, text search and selected metadata readers. These grants permit reading and computing results; they do not authorize changing stored objects or administering the server. Dataset routine and trigger *mutation* scenarios remain writer tests. The native read tests check denial of every user-defined stored routine rather than invoking those scenarios as `demo`.

Two employee views originally called ported helpers that use `set_config` to mirror MySQL session variables. Initialization replaces those view expressions with equivalent scalar read queries. The writer's helper routines retain their original definitions and privileges; `demo` receives no user-routine execution grant. The repository's view fingerprints and a native session-state test validate the replacement. XPath evaluation and encoding conversion remain available for the AdventureWorks and Wikipedia read views.

Database ACLs are initialized during creation. The preloaded policy checks the creator and any namespace restriction, then closes public connection and temporary-object privileges in PostgreSQL’s catalog before the server copies database files. If confirmation fails, the new database is closed to every connection. The compiler and server headers are confined to an image build stage.

Routine defaults are closed globally for `admin` and `postgres`. An event trigger inherited from both templates also closes public execution on newly created routines, including routines created by a later role in a later schema. Policy schema/function/event-trigger objects, the `megasamples_policy` schema included, are packaged as extension members so dataset dump/restore does not recreate copies already inherited from `template0`; the extension is installed in `pg_catalog`, so it depends on no schema a copy owner could drop. The trigger runs with the fixed search path `pg_catalog, pg_temp`, with every name schema-qualified, in a schema inaccessible to `demo`; its own function is not executable by `demo`. Trusted owners and superusers can deliberately grant privileges or disable policy; this is an initialization and default-creation policy, not a sandbox against administrators.

MySQL gives `demo` exactly `SELECT, SHOW VIEW` on the working schemas and on explicitly enabled foreign namespaces (each pattern's underscores escaped), `SELECT` on the registry tables `megasamples.datasets` and `megasamples.copy_service`, and `USAGE`; nothing on other schemas, and no `CREATE TEMPORARY TABLES`, stored-routine `EXECUTE`, write, grant or administrative privileges. The image's own grant generator (`megasamples/mysql_templates.py`) is the source, and `megasamples test-image` and the native suite assert the exact set. *(Historical: the evidence of 2026-11-18 below was taken when `demo` held `SELECT, SHOW VIEW ON *.*`.)* The tests inspect its actual grants and attempt temporary-table creation and every direct stored-routine call. Writer grants remain unchanged. These are server account grants, not a SQL statement classifier: ordinary session control and MySQL built-ins are not governed by stored-routine `EXECUTE` ACLs. The executable [boundary probe](validation/strict-read-mysql-boundary.py) confirms persistent write/DDL denials in every sample database and also confirms that `demo` can acquire and release a built-in named lock. The strict named-lock denial criterion is **Failed**. Enforcing “only reads” across these MySQL built-ins is **Unsupported by stored-routine grants**. It would require an additional statement/function restriction layer; this PR does not supply one. MySQL documents [named locks](https://dev.mysql.com/doc/refman/9.7/en/locking-functions.html) separately from [stored-routine execution privileges](https://dev.mysql.com/doc/refman/9.7/en/privileges-provided.html), read **2026-11-18 09:56:36 UTC**. SQLite has no server accounts; a read-only client must open its files read-only. Its [omitted SQL features](https://www.sqlite.org/omitted.html), read **2026-11-18 10:56:21 UTC**, document the absence of GRANT/REVOKE.

Run native privilege tests with `MEGASAMPLES_NATIVE_READ_TESTS=1` after sourcing the supplied environment. `tests/test_strict_read_native.py` requires `DL077_ISOLATED_GRAPH` (the isolated store, checked first), each engine's container named in `STRICT_READ_POSTGRES_CONTAINER` or `STRICT_READ_MYSQL_CONTAINER`, and `STRICT_READ_OWNER`, which each container's ownership label must equal; it then uses only the container IDs it checked. Regular `make test-image` checks also cover temporary-object denial, large-object denial and forbidden PostgreSQL routine execution. The canonical dataset matrix runs counts, fingerprints, foreign-key/index checks and views as `demo`. At each reset checkpoint a supplementary native matrix reads every complete table: PostgreSQL folds native row MD5 values, MySQL uses native extended table checksums, and SQLite checks both runtime files by SHA-256. These reset fingerprints compare within an engine; they do not replace the repository's canonical cross-engine fingerprints.
