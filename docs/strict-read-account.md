The `demo` account reads the sample data. PostgreSQL initialization removes database `TEMPORARY` and routine `EXECUTE` inherited from `PUBLIC`. `admin` receives explicit temporary-object rights for write workloads; its previous effective routine rights are preserved before removing the public grants. The superuser retains its rights. This policy applies to the registry, maintenance database, sample databases and both templates.

The built-in read policy lives in [read-routine-names.sql](../engines/postgres/init/read-routine-names.sql). Each name has a reason. Initdb operators and casts also retain their nonvolatile implementation functions; selected upstream `information_schema` helpers retain execution for column and key metadata. Initialization admits only its immutable/stable overloads in `pg_catalog` with initdb object identifiers and without `SECURITY DEFINER`. Metadata helper definitions were checked against the upstream source. No user routine qualifies merely because it declares itself `STABLE`. Large-object creation/import, sequence advancement, configuration changes, advisory locks, notifications and server-management routines receive no `demo` grant. The [complete observed list](validation/strict-read-executable-routines.md) records every executable signature with its individual reason; its set is identical across all inventoried databases.

The policy deliberately excludes transaction-ID allocation (`txid_current` and `pg_current_xact_id`), although these built-ins are classified `STABLE`. It retains query arithmetic, text/date/JSON transformations, aggregates, window functions, text search and selected metadata readers. These grants permit reading and computing results; they do not authorize changing stored objects or administering the server. Dataset routine and trigger *mutation* scenarios remain writer tests. The native read tests check denial of every user-defined stored routine rather than invoking those scenarios as `demo`.

Two employee views originally called ported helpers that use `set_config` to mirror MySQL session variables. Initialization replaces those view expressions with equivalent scalar read queries. The writer's helper routines retain their original definitions and privileges; `demo` receives no user-routine execution grant. The repository's view fingerprints and a native session-state test validate the replacement. XPath evaluation and encoding conversion remain available for the AdventureWorks and Wikipedia read views.

Database ACLs are not copied from templates. A small `ProcessUtility` hook, loaded through `shared_preload_libraries`, therefore runs ordinary `REVOKE TEMPORARY ... FROM PUBLIC` and `GRANT TEMPORARY ... TO admin` after `CREATE DATABASE` and before its transaction commits. It executes as the creator, without elevating privileges, and a failure aborts database creation. Both default-template and explicit-template creation paths are tested. The compiler and server headers are confined to an image build stage; the final image contains only the shared library.

Routine defaults are closed globally for `admin` and `postgres`. An event trigger inherited from both templates also closes public execution on newly created routines, including routines created by a later role in a later schema. Policy schema/function/event-trigger objects are packaged as extension members so dataset dump/restore does not recreate copies already inherited from `template0`. The trigger runs with a fixed `pg_catalog` search path in a schema inaccessible to `demo`; its own function is not executable by `demo`. Trusted owners and superusers can deliberately grant privileges or disable policy; this is an initialization and default-creation policy, not a sandbox against administrators.

MySQL already gives `demo` exactly `SELECT, SHOW VIEW ON *.*`, without `CREATE TEMPORARY TABLES`, stored-routine `EXECUTE`, write, grant or administrative privileges. The tests inspect its actual grants and attempt temporary-table creation and execution of every stored routine. Writer grants remain unchanged. These are server account grants, not a SQL statement classifier: ordinary session control and MySQL built-ins are not governed by stored-routine `EXECUTE` ACLs. SQLite has no server accounts; a read-only client must open its files read-only.

Run native privilege tests with `MEGASAMPLES_NATIVE_READ_TESTS=1` in the isolated tools container after sourcing the supplied environment. `tests/test_strict_read_native.py` refuses a different container store. Regular `make test-image` checks also cover temporary-object denial, large-object denial and forbidden PostgreSQL routine execution. The canonical dataset matrix runs counts, fingerprints, foreign-key/index checks and views as `demo`. At each reset checkpoint a supplementary native matrix reads every complete table: PostgreSQL folds native row MD5 values, MySQL uses native extended table checksums, and SQLite checks both runtime files by SHA-256. These reset fingerprints compare within an engine; they do not replace the repository's canonical cross-engine fingerprints.
